1. EXECUTIVE SUMMARY & SYSTEM OVERVIEW
--------------------------------------------------------------------------------
CloudGuard is an enterprise-grade, full-stack Cloud Security Posture Management
(CSPM) platform built to audit, enumerate, monitor, and remediate multi-account
Amazon Web Services (AWS) environments.

The system solves critical enterprise security challenges:
1. Multi-Account Blind Spots: Centralized visibility across multiple AWS accounts
   and regions without requiring permanent IAM access keys or credentials.
2. Compliance Visibility: Automated mapping and evaluation against six major
   industry security benchmarks (CIS AWS Foundations, SOC 2 Type II, PCI-DSS
   v4.0, HIPAA Security, NIST 800-53, and ISO 27001).
3. Resource Misconfigurations: Live inventory enumeration of cloud assets (S3,
   EC2, IAM, VPC, RDS, Lambda, Access Analyzer) identifying unencrypted storage
   and public exposures.
4. Remediation Bottlenecks: Instant, contextual remediation code generated by
   Groq-hosted LLaMA 3.3 70B (providing copy-pasteable AWS CLI commands,
   production Terraform HCL snippets, AWS Management Console steps, and CLI
   verification commands) backed by an interactive follow-up chat engine.

2. TECHNOLOGY STACK SPECIFICATION
--------------------------------------------------------------------------------
Frontend Tier:
- Framework: Next.js 15 (App Router with Route Groups and Server/Client Components)
- Core Library: React 19, TypeScript 5.7+
- Styling: Tailwind CSS 3.4, Radix/Shadcn UI Primitives, Lucide React
- Visualizations: Recharts 2.15 (Radar charts, Donut charts, Bar charts, Area charts)
- Authentication: Clerk Next.js SDK (@clerk/nextjs 6.12+)
- Markdown Rendering: React-Markdown 9.0 (for AI remediation plans and CLI snippets)

Backend & API Tier:
- Framework: FastAPI 0.115+ (Python 3.11/3.12+)
- ASGI Server: Uvicorn with standard workers
- ORM & Query Engine: SQLAlchemy 2.0 (Asyncio) with asyncpg driver
- Validation & Settings: Pydantic v2, Pydantic-Settings
- Schema Migrations: Alembic 1.14+
- HTTP Client: HTTPX 0.28+

Security & Cloud Engines:
- Cloud SDK: Boto3 1.35+ (AWS SDK for Python) with STS AssumeRole
- Compliance Audit Engine: Prowler 5.x CLI (OCSF JSON Schema standard)
- AI LLM Inference: Groq Cloud API (AsyncGroq SDK running llama-3.3-70b-versatile)

Data & Async Queue Tier:
- Primary Database: PostgreSQL 16 (Relational DB for accounts, resources, findings, scans, cache)
- In-Memory Cache & Message Broker: Redis 7 (STS credential caching & ARQ job queues)
- Async Task Queue: ARQ 0.26+ (Async Redis Queue for background Prowler subprocess jobs)
- Containerization: Docker, Docker Compose (frontend, api, worker, postgres, redis)

3. USER PERSONAS & KEY STAKEHOLDERS
--------------------------------------------------------------------------------
1. Cloud Security Engineer:
   - Primary user conducting routine compliance audits.
   - Monitors security posture score and investigates critical findings.
   - Copies Terraform or AWS CLI remediation code directly into deployment pipelines.
   - Validates fixes using the interactive single-finding rescan button.

2. DevOps / Site Reliability Engineer (SRE):
   - Integrates AWS accounts into CloudGuard using IAM Cross-Account Roles.
   - Tracks resource inventory counts, public exposures, and unencrypted databases.
   - Consults the AI Assistant for infrastructure-as-code migration guidance.

3. Chief Information Security Officer (CISO) & Compliance Auditor:
   - Reviews high-level compliance radar scores across CIS, SOC 2, HIPAA, PCI-DSS.
   - Analyzes risk distributions and tracks remediation velocity across environments
     (production, staging, development, testing).

4. FUNCTIONAL REQUIREMENTS (FR)
--------------------------------------------------------------------------------

FR-1: Multi-Account AWS Onboarding & STS Delegation Handshake
- FR-1.1: System shall register target AWS accounts using Account ID (12 digits),
  Account Name, Cross-Account IAM Role ARN, Environment tag, and Target Regions.
- FR-1.2: System shall generate a cryptographically unique External ID (prefixed
  with 'cspm-ext-') upon registration to mitigate confused deputy attacks.
- FR-1.3: System shall validate STS AssumeRole connectivity during account setup
  and mark status as 'connected', 'pending', or 'error'.
- FR-1.4: System shall allow updating account metadata and deleting accounts with
  cascading cleanup of associated findings, resources, and scan logs.

FR-2: Cloud Resource Inventory Enumeration (Boto3 Engine)
- FR-2.1: System shall discover global AWS assets: S3 buckets (checking public
  access blocks, ACLs, and default encryption) and IAM users (access keys, passwords).
- FR-2.2: System shall discover regional AWS assets across specified regions:
  EC2 instances (public IPs, VPC, instance state), VPCs (CIDR, default flags),
  Security Groups (public 0.0.0.0/0 ingress rules), RDS DB instances (engine,
  public accessibility, KMS storage encryption), and Lambda functions.
- FR-2.3: Discovered resources shall be normalized and upserted into the
  'cloud_resources' table with tags, public flags, encryption flags, and raw JSON metadata.
- FR-2.4: System shall calculate service-level summaries (total count, public count,
  unencrypted count) per connected account.

FR-3: Compliance Auditing & Security Scanning (Prowler 5.x Subprocess Engine)
- FR-3.1: System shall support triggering 'full' compliance scans (Boto3 + Prowler)
  or 'resources_only' discovery scans.
- FR-3.2: Prowler runner shall execute isolated CLI subprocesses outputting
  standardized JSON-OCSF (Open Cybersecurity Schema Framework) records.
- FR-3.3: Findings parser shall extract check ID, severity (critical, high,
  medium, low, info), status (pass, fail, manual, muted), service, region, title,
  description, recommendation, and compliance framework mappings.
- FR-3.4: Finding ingestion shall deduplicate records in-memory and perform
  PostgreSQL ON CONFLICT DO UPDATE upserts against the composite constraint
  (account_id, check_id, resource_id).
- FR-3.5: Scan state machine shall track lifecycle statuses: 'pending' -> 'running'
  -> 'completed' or 'failed', logging duration and resource/finding counts.

FR-4: AI-Powered Remediation & Interactive Chat (Groq LLaMA 3.3)
- FR-4.1: When requested for a security finding, the system shall generate a
  deterministic 5-section remediation plan:
  1. Impact Assessment (threat modeling and security implications)
  2. AWS CLI Fix (exact command-line execution steps)
  3. Terraform Fix (production-grade HCL code blocks)
  4. AWS Console Steps (numbered UI navigation instructions)
  5. Verification (CLI queries to prove remediation effectiveness)
- FR-4.2: Two-Tier Remediation Cache: The system shall check PostgreSQL
  'remediation_cache' by (check_id, severity, service) before invoking the LLM.
  On cache hits, response is served in <50ms with 0 token consumption.
- FR-4.3: Interactive Follow-Up Chat: Users can ask contextual questions regarding
  the finding or remediation plan with full conversation history preserved in the drawer.

FR-5: Single-Finding Rescan & Verification
- FR-5.1: Users can trigger a targeted rescan on individual findings.
- FR-5.2: Finding status immediately transitions to 'rescanning' with UI spinner.
- FR-5.3: Upon targeted verification, status transitions to 'pass' (green checkmark)
  or 'fail' (alerting engineer to unresolved issues).

FR-6: Executive Dashboard & Telemetry Visualization
- FR-6.1: Real-time calculation of Global Security Score (0-100%) based on ratio
  of passing checks to total evaluated findings.
- FR-6.2: Severity breakdown counters for Critical, High, Medium, Low, Info alerts.
- FR-6.3: Radar / Compliance breakdown scores across CIS AWS Foundations, SOC 2
  Type II, PCI-DSS v4.0, HIPAA Security, NIST 800-53, and ISO 27001.
- FR-6.4: Interactive Asset Inventory breakdown by service and type.
- FR-6.5: Live scan activity indicator badge reflecting background job execution.

FR-7: Mock Data Fallback Engine (Client Resilience)
- FR-7.1: Frontend provides a standalone mock mode controlled via `USE_MOCK_DATA`
  in `lib/mock-data.ts`.
- FR-7.2: Allows full UI inspection, demo capabilities, and client-side testing
  even when backend containers or AWS credentials are unavailable.

5. NON-FUNCTIONAL REQUIREMENTS (NFR)
--------------------------------------------------------------------------------

NFR-1: Security & Zero-Trust Architecture
- Zero Plaintext Credentials: No AWS access keys stored in application code or DB.
- Cross-Account Delegation: Target accounts accessed strictly via STS AssumeRole.
- Confused Deputy Protection: External ID validation enforced on all STS sessions.
- Least Privilege IAM: Scan role requires only SecurityAudit and ViewOnlyAccess.
- Cache Security: Temporary STS tokens cached in Redis expire within 50 minutes (TTL 3000s).

NFR-2: Performance & Scalability
- Async Architecture: FastAPI endpoints leverage non-blocking async/await for all
  I/O, database sessions, and Redis commands.
- Concurrent Scanning: Independent ARQ worker processes scans asynchronously
  without blocking API request threads.
- Query Optimization: Indexed database queries for paginated finding retrieval
  supporting filter parameters (severity, service, status).
- AI Caching: LLM response caching eliminates redundant token costs and latency
  for common check findings across accounts.

NFR-3: Reliability & Fault Tolerance
- Graceful Degradation: If Prowler CLI is not found or fails, resource discovery
  still completes and stores inventory assets.
- Fallback AWS Credentials: If AssumeRole fails due to permission latency, the
  system falls back safely to direct environment credentials.
- Automatic Polling: Frontend polls running scan status every 3 seconds until
  completion or failure, updating all UI components reactively.

7. DATABASE SCHEMA SPECIFICATION (PostgreSQL 16)
--------------------------------------------------------------------------------

Table: cloud_accounts
- id: UUID (Primary Key, default uuid_generate_v4())
- account_id: VARCHAR(12) (Unique, Not Null, 12-digit AWS Account ID)
- name: VARCHAR(255) (Not Null, Display Name)
- role_arn: VARCHAR(512) (Not Null, IAM Role ARN to assume)
- external_id: VARCHAR(64) (Not Null, Unique STS External ID)
- environment: VARCHAR(50) (Default 'production': production, staging, development, testing)
- regions: VARCHAR[] (Array of AWS region identifiers, e.g. ['us-east-1', 'ap-south-1'])
- status: VARCHAR(20) (Default 'pending': connected, pending, error, disconnected)
- created_at: TIMESTAMP WITH TIME ZONE (Default NOW())
- updated_at: TIMESTAMP WITH TIME ZONE (Default NOW())
- last_scan_at: TIMESTAMP WITH TIME ZONE (Nullable)

Table: cloud_resources
- id: UUID (Primary Key)
- account_id: VARCHAR(12) (Foreign Key -> cloud_accounts.account_id)
- resource_id: VARCHAR(512) (Not Null, ARN or unique AWS identifier)
- resource_type: VARCHAR(100) (Not Null, e.g. AWS::S3::Bucket, AWS::EC2::Instance)
- service: VARCHAR(50) (Nullable, e.g. s3, ec2, iam, vpc, rds, lambda)
- region: VARCHAR(50) (Nullable, e.g. us-east-1, global)
- tags: JSONB (Key-value tags dictionary)
- is_public: BOOLEAN (Nullable, True if resource allows public access)
- encrypted: BOOLEAN (Nullable, True if resource has encryption enabled)
- raw_data: JSONB (Service-specific configuration payload)
- last_seen: TIMESTAMP WITH TIME ZONE (Default NOW())
- Unique Constraint: uq_account_resource (account_id, resource_id)

Table: scans
- id: UUID (Primary Key)
- account_id: VARCHAR(12) (Foreign Key -> cloud_accounts.account_id)
- scan_type: VARCHAR(20) (Default 'full': full, resources_only)
- status: VARCHAR(20) (Default 'pending': running, completed, failed)
- started_at: TIMESTAMP WITH TIME ZONE (Default NOW())
- finished_at: TIMESTAMP WITH TIME ZONE (Nullable)
- findings_count: INTEGER (Default 0)
- resources_scanned: INTEGER (Default 0)
- error_message: TEXT (Nullable)
- worker_id: VARCHAR(100) (Nullable)

Table: findings
- id: UUID (Primary Key)
- account_id: VARCHAR(12) (Foreign Key -> cloud_accounts.account_id)
- scan_id: UUID (Nullable, Foreign Key -> scans.id)
- check_id: VARCHAR(100) (Not Null, Prowler check identifier)
- resource_id: VARCHAR(512) (Nullable, Resource identifier or ARN)
- resource_type: VARCHAR(100) (Nullable, AWS resource type)
- service: VARCHAR(50) (Nullable, AWS service name)
- region: VARCHAR(50) (Nullable, AWS region or global)
- title: TEXT (Not Null, Concise description of the check finding)
- status: VARCHAR(20) (Not Null: pass, fail, manual, rescanning, not_found, error)
- severity: VARCHAR(10) (Not Null: critical, high, medium, low, info)
- compliance_type: VARCHAR(100) (Nullable, Comma-separated framework list)
- description: TEXT (Nullable, Detailed risk explanation)
- recommendation: TEXT (Nullable, High-level remediation advice)
- compliance: JSONB (Framework section and requirement mappings)
- remediation: JSONB (Tooling and CLI documentation links)
- raw_data: JSONB (Raw OCSF finding record from Prowler)
- updated_at: TIMESTAMP WITH TIME ZONE (Default NOW())
- Unique Constraint: uq_account_check_resource (account_id, check_id, resource_id)

Table: remediation_cache
- id: UUID (Primary Key)
- check_id: VARCHAR(100) (Not Null, Unique check identifier)
- severity: VARCHAR(10) (Not Null)
- service: VARCHAR(50) (Nullable)
- ai_response: TEXT (Not Null, Generated Markdown remediation guide)
- model: VARCHAR(100) (Model identifier, e.g. llama-3.3-70b-versatile)
- tokens_used: INTEGER (Nullable)
- created_at: TIMESTAMP WITH TIME ZONE (Default NOW())
- Unique Constraint: uq_check_severity_service (check_id, severity, service)

8. REST API SPECIFICATION & CONTRACTS
--------------------------------------------------------------------------------
Base URL: /api/cloud-security (Proxied via Next.js to FastAPI Backend)

1. Accounts API:
- GET /accounts
  Description: List all connected AWS accounts.
  Response: Array of AccountResponse objects.
- POST /accounts
  Description: Register a new AWS account.
  Request Body: { account_id: string, name: string, role_arn: string, environment: string, regions: string }
  Response: 201 Created with AccountResponse (includes generated external_id).
- PUT /accounts/{account_id}
  Description: Update existing account name, role_arn, environment, or regions.
  Response: 200 OK with updated AccountResponse.
- DELETE /accounts/{account_id}
  Description: Remove account and delete associated data.
  Response: { status: "deleted" }
- GET /accounts/{account_id}/validate
  Description: Test STS AssumeRole authentication handshake.
  Response: { valid: boolean, error?: string }

2. Scans API:
- POST /scan/{account_id}?include_prowler=true|false
  Description: Trigger asynchronous background scan job.
  Response: 200 OK with ScanResult (status: "running").
- GET /scan/{scan_id}/status
  Description: Retrieve real-time progress and status of a scan.
  Response: ScanResult (status: "running" | "completed" | "failed").
- GET /scan/{account_id}/history?limit=20
  Description: Retrieve list of historical scans for an account.
  Response: Array of ScanResult objects.

3. Findings API:
- GET /findings?account_id={id}&page=1&page_size=50&severity={s}&service={svc}&statuses={pass,fail}
  Description: Paginated query for security findings with filtering.
  Response: { items: Finding[], total: number, page: number, page_size: number, total_pages: number }
- GET /findings/{finding_id}
  Description: Get complete detail and OCSF metadata for a specific finding.
  Response: Finding object.
- POST /findings/{finding_id}/rescan
  Description: Request single-finding re-verification check.
  Response: { id: string, status: "rescanning", updated_at: string }

4. Resources API:
- GET /resources/{account_id}
  Description: List all discovered cloud inventory assets for an account.
  Response: Array of CloudResource objects.
- GET /resources/{account_id}/summary
  Description: Service-level aggregation of total, public, and unencrypted assets.
  Response: Array of { service: string, count: number, public_count: number, unencrypted_count: number }.

5. Statistics & Dashboard API:
- GET /stats/{account_id}
  Description: Aggregated telemetry for executive dashboard.
  Response: {
    security_score: number (0-100),
    total_alerts: number,
    alerts_by_severity: { critical: N, high: N, medium: N, low: N, info: N },
    compliance_status: { "CIS AWS Foundations": N, "SOC 2 Type II": N, ... },
    asset_inventory: [{ name: service, value: count }],
    total_resources: number,
    last_scan: ISO8601 string,
    recent_findings: Finding[]
  }

6. AI Remediation API:
- POST /remediation/resolve
  Description: Retrieve or generate 5-part AI remediation guide.
  Request Body: { title, description, recommendation, severity, service, resource_type, resource_id, region }
  Response: { steps: string (Markdown), model: string, tokens_used: number }
- POST /remediation/chat
  Description: Follow-up contextual question answering for a specific finding.
  Request Body: { finding_context: string, messages: [{ role: "user"|"assistant", content: string }] }
  Response: { reply: string, model: string }
